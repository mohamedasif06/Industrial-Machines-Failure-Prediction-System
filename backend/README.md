# FastAPI backend

This backend is an isolated Phase 6 service. It delegates predictions to the existing `src/inference.py` function and delegates synthetic sensor generation to `src/simulator.py`. It does not retrain a model, duplicate Type encoding, or alter the React frontend. Telemetry is explicitly synthetic; a predicted class and probability estimate are not physical confirmation or a guaranteed future failure time.

## Install and run in Windows PowerShell

Run from the project root, using the existing virtual environment:

```powershell
.\.venv\Scripts\python.exe -m pip install -r .\backend\requirements.txt
Set-Location .\backend
..\.venv\Scripts\python.exe -m app
```

The default address is `http://127.0.0.1:8000`; interactive OpenAPI documentation is at `/docs`. Configure runtime options before starting the process:

```powershell
$env:BACKEND_HOST = "127.0.0.1"
$env:BACKEND_PORT = "8000"
$env:BACKEND_CORS_ORIGINS = "http://localhost:5173,http://127.0.0.1:5173"
$env:BACKEND_EVENT_HISTORY_LIMIT = "1000"
```

The default CORS origins are the local Vite development URLs. CORS allows only GET/POST and `Content-Type`, without credentials. Event history is in memory and resets when the process restarts.

## API

| Method | Path | Behavior |
| --- | --- | --- |
| GET | `/api/health` | Backend health and saved-model metadata/artifact availability. |
| POST | `/api/predict` | Validates and predicts from exactly the six agreed fields. |
| GET | `/api/machines` | Latest event per machine plus a machine count. |
| GET | `/api/machines/{machine_id}` | Latest event for one machine; 404 if absent. |
| GET | `/api/events?limit=100` | Newest retained events (limit 1–500) and returned event count. |
| GET | `/api/alerts` | Retained managed alert episodes, active/resolved totals, and lifecycle thresholds. |
| GET | `/api/simulator/status` | Simulator running state and any last generation error. |
| POST | `/api/simulator/start` | Starts existing simulator logic with bounded configuration options. |
| POST | `/api/simulator/stop` | Stops simulator; safe if it is already stopped. |
| WS | `/ws/telemetry` | Receives each newly accepted synthetic event as JSON. |

The prediction JSON request has precisely these keys (unknown and missing keys are rejected):

```json
{
  "Type": "L",
  "Air temperature [K]": 300.0,
  "Process temperature [K]": 310.0,
  "Rotational speed [rpm]": 1500,
  "Torque [Nm]": 40.0,
  "Tool wear [min]": 100
}
```

`Type` accepts the original `L`, `M`, or `H` category. The existing inference function applies the saved Type mapping. Prediction response fields include `predicted_class`, `predicted_label`, `model_name`, a probability note, and `estimated_failure_probability` when available. The probability is a model estimate, not a calibrated promise.

## Managed alert lifecycle

Every unique telemetry event remains in the bounded event history. Separately, the backend creates one managed alert episode per machine and `failure_associated_prediction` condition after two consecutive class 1 results by default. Further class 1 events update its latest event, probability, `last_seen`, and occurrence count. Three consecutive class 0 results resolve it by default; an isolated class 0 does not. A later confirmed class 1 streak opens a new episode. Both thresholds are configurable with positive integer environment variables `BACKEND_ALERT_ACTIVATION_THRESHOLD` and `BACKEND_ALERT_RECOVERY_THRESHOLD`. `BACKEND_ALERT_HISTORY_LIMIT` (default 1000) limits retained episodes; active alerts are not evicted to satisfy the cap. Alert state and telemetry history are in memory and reset when the backend process restarts. Alert lifecycle WebSocket messages use `event_type` values `alert.created`, `alert.updated`, and `alert.resolved`; raw telemetry event messages continue to be published unchanged.

## Simulator controls

To start a synthetic simulator with defaults, send an empty object to `POST /api/simulator/start`. It generates a reading tick every 2 seconds by default. Optional fields are `machine_count` (1–100), `interval_seconds` (>0, up to 3600; reported by simulator status), `mode` (`normal`, `fault_scenario`, or `mixed`), `machine_modes`, `seed`, `wear_min`, `wear_max` (at most 253), and `wear_increment`. Mixed mode requires at least two machines and alternates normal and fault-scenario generation across stable machine IDs unless explicitly configured. For example, `{"mode":"mixed","machine_count":3,"machine_modes":["normal","fault_scenario","normal"]}` assigns modes in machine ID order; the list must include both modes and match the machine count. A running simulator returns HTTP 409 to another start request. These readings are generated by the existing simulator; every output is passed through the saved inference function and the backend does not force model outputs. Stopping the API process also stops its task.

## Event shape

WebSocket messages and REST event objects use the existing simulator event fields:

```json
{
  "timestamp": "2026-10-10T10:00:00.000Z",
  "machine_id": "SIM-MACHINE-001",
  "simulation_mode": "normal",
  "simulated": true,
  "Type": "L",
  "Air temperature [K]": 300.0,
  "Process temperature [K]": 310.0,
  "Rotational speed [rpm]": 1500,
  "Torque [Nm]": 40.0,
  "Tool wear [min]": 100.0,
  "predicted_class": 0,
  "predicted_label": "no failure",
  "model_name": "XGBoost",
  "estimated_failure_probability": 0.01
}
```

Only events with `simulated: true` are accepted. Duplicate machine/timestamp pairs are ignored. The bounded in-memory store serves latest-per-machine views and recent event history; a process restart clears both. No physical sensor, breakdown confirmation, persistence, authentication, or deployment integration exists in this phase.

## Tests

Run from the project root:

```powershell
.\.venv\Scripts\python.exe -m pytest .\backend\tests -q
```

Run the backend suite (including the existing Phase 4 simulator regression tests) from the project root. Disabling pytest's on-disk cache avoids cache writes in restricted or synced folders:

```powershell
.\.venv\Scripts\python.exe -m pytest -p no:cacheprovider .\backend\tests .\tests\test_simulator.py -q
```

The backend suite includes mocked unit checks and an integration check that calls the saved model through the existing inference function without retraining.
